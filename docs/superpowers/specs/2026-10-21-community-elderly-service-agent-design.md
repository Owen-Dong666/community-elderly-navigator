# 社区老人办事导航智能体设计规格

## 1 项目目标

本项目为小学组“智能体设计与应用”作品，面向不熟悉智能手机和社区办事流程的老人。用户可以用自然语言询问社区活动或便民服务，系统从社区知识库检索可靠资料，规划清晰的办事步骤，并通过大字屏幕、语音播报和地图地点指示帮助用户完成事项。

第一阶段交付可在电脑上独立运行的智能体和浏览器 K10 模拟器。模拟器复现 K10 的屏幕、A/B 按钮、扬声器状态和六个地图 LED。后续实体 K10 通过设备适配层接入，不改变知识检索、规划、安全校验和会话状态等核心逻辑。

## 2 竞赛要求对应关系

系统必须清楚体现以下智能体链路：

1. 感知：接收用户的语音或文字问题。
2. 规划：检索社区资料，由大语言模型把资料整理为可执行的办事计划。
3. 行动：更新屏幕、播报当前步骤、切换步骤并点亮目标地点。

大语言模型是规划和自然语言理解的核心，但事实必须来自本地社区知识库。项目不得依赖模型记忆回答社区时间、地点、材料和联系方式。第一阶段可以调用云端兼容 API，后期必须能切换至 Ollama 中的 Qwen3 0.6B。现场断网时核心知识库、检索、安全校验、会话管理和设备控制仍在本机运行。

## 3 目标用户与设计原则

### 3.1 目标用户

主要用户是视力、听力、记忆或智能设备操作能力可能下降的社区老人。展示与讲解同时面向小学组评委，因此系统结构应直观、功能边界清楚，学生能够用生活化语言解释每个模块。

### 3.2 设计原则

- 大字、高对比度、少按钮、少层级。
- 一次只显示一个办事步骤，避免信息过载。
- 每次切换步骤后自动播报当前内容。
- 事实优先于流畅表达；无法确认时明确提示工作人员确认。
- 关键行为由程序规则保证，不把防止编造完全交给提示词。
- 首版保持小而完整，不引入不必要的数据库、向量服务或复杂前端框架。

## 4 第一阶段范围

### 4.1 包含内容

- 电脑端 Python 智能体服务。
- 浏览器 K10 模拟器。
- 语音输入入口、文字输入备用入口和浏览器语音播报。
- 虚构社区示例知识库。
- 云端 OpenAI 兼容接口、Ollama 接口和确定性模拟模型接口。
- 知识检索、办事规划、模型输出校验、降级生成和会话管理。
- 屏幕、步骤、语音状态和六个地图 LED 的模拟。
- 自动化测试与演示场景。
- 为 Mind+ 和实体 K10 预留的串口消息协议。

### 4.2 不包含内容

- 第一阶段不连接实体 K10 或 DFR1231 扩展板。
- 不接入真实社区后台、政务系统或个人身份数据。
- 不保存语音录音、身份证号码、手机号等个人信息。
- 不承诺知识库之外的政策解释、资格审批或办理结果。
- 不使用向量数据库；首版数据量不足以证明其必要性。
- 不实现用户登录、多社区管理和远程后台。

## 5 总体架构

系统采用七层结构，各层通过明确的数据对象连接。

1. 感知层将语音识别结果或文字输入规范化为查询文本。
2. 知识库保存地点、服务、活动、材料、开放时间和步骤。
3. 检索层按名称、别名、关键词、服务类别和适用人群筛选候选记录。
4. 规划层让大语言模型依据候选记录生成结构化计划。
5. 安全校验层核对服务、地点、时间、材料、步骤和来源记录。
6. 会话与行动层维护当前步骤，并产生屏幕、语音和 LED 指令。
7. 设备适配层把统一设备状态呈现到浏览器，后续也可编码为串口消息。

前端不直接访问模型或知识库。所有判断都经过电脑端服务，保证模拟器和实体 K10 的行为一致。

## 6 核心组件

### 6.1 感知模块

浏览器优先提供麦克风按钮，使用可用的浏览器语音识别能力把语音转成文字。由于不同浏览器和网络环境对语音识别支持不同，文字输入始终可用，并在界面上标明“测试输入”。第一阶段不把浏览器语音识别视为离线能力。

模块只输出清理后的查询文本，不保存音频。空输入、纯标点和过长输入在进入检索前被拒绝，并给出简短提示。

### 6.2 社区知识库

知识库使用可人工阅读和修改的 JSON 文件。首版虚构社区包含以下六个地点：

1. 小区入口
2. 社区中心
3. 卫生站
4. 活动室
5. 服务大厅
6. 便民驿站

首版提供约十五项覆盖活动报名、健康服务、养老服务和生活帮助的示例记录，包括书法班、太极班、合唱活动、智能手机课堂、健康讲座、血压测量、社保咨询、高龄津贴咨询、居家养老申请、养老资格认证、助餐服务、水电报修、法律咨询、志愿陪诊和社区图书借阅。

所有数据必须明确标注为演示数据，不得在展示中暗示其为真实社区通知。

地点记录包含：

- `id`：稳定地点编号。
- `name`：屏幕显示名称。
- `led_index`：一至六的地图 LED 编号。
- `description`：地图位置提示。

服务记录包含：

- `id`：稳定服务编号。
- `name`：正式名称。
- `aliases`：老人可能使用的常见说法。
- `category`：活动、健康、养老或生活服务。
- `audience`：适用人群说明。
- `summary`：一句话介绍。
- `schedule`：开放或活动时间文字。
- `location_id`：关联地点编号。
- `materials`：需要准备的材料列表。
- `steps`：按顺序排列的固定事实步骤。
- `keywords`：用于检索的关键词。
- `contact_note`：需要工作人员确认时的说明。
- `requires_confirmation`：资料本身是否要求人工确认。

### 6.3 检索模块

检索不依赖模型。模块对查询进行轻量规范化，并按以下顺序计算候选：

1. 服务名称或别名直接命中。
2. 关键词命中数量。
3. 类别和适用人群词命中。
4. 中文字符相似度用于处理少量近似说法。

系统最多把三条候选记录交给规划层。没有达到最低置信度的候选时直接进入“未找到”流程，不要求模型猜测。

### 6.4 模型提供者

模型通过统一 `ModelProvider` 接口调用，输入是系统约束、用户问题和候选知识记录，输出是结构化计划。

- `OpenAICompatibleProvider` 使用可配置的 `base_url`、`api_key` 和 `model`，用于前期云端测试。
- `OllamaProvider` 默认面向本机 `http://127.0.0.1:11434`，模型名称可配置为 Qwen3 0.6B 对应标签。
- `MockProvider` 根据固定规则返回结果，用于断网演示和自动测试。

API 密钥只从环境变量读取，不写入源码、知识库或浏览器。配置切换不改变上层调用方式。

### 6.5 规划与校验模块

规划结果使用以下概念结构：

```text
PlanResult
  status: ready | needs_clarification | not_found | error
  service_id: string or null
  service_name: string
  summary: string
  location_id: string or null
  schedule: string
  materials: list of string
  steps: list of PlanStep
  confirmation_message: string or null
  source_record_ids: list of string

PlanStep
  index: positive integer
  title: short string
  instruction: string
  speech: string
```

校验器必须确认：

- `service_id` 和 `source_record_ids` 属于候选记录。
- `location_id` 存在并与知识记录一致。
- 时间、材料和关键办理事实能够在来源记录中找到。
- 步骤非空、顺序连续且数量不超过六步。
- 每一步适合在小屏幕显示和短句播报。

模型输出非法时只重试一次。第二次失败后，程序直接根据最高置信度知识记录生成固定步骤，不把非法内容展示给用户。

### 6.6 会话与设备状态模块

每次成功查询创建一个短期会话，保存计划、当前步骤和设备状态。第一阶段会话只保存在内存，不保存个人身份信息。

统一设备状态包含：

- 页面状态：待机、聆听、查询、规划、展示或错误。
- 当前服务名称。
- 当前步骤序号和总步骤数。
- 屏幕标题、正文和辅助信息。
- 待播报文字和播报状态。
- 六个 LED 的开关状态。

设备事件只有三类：

- `QUERY`：提交查询文本。
- `BUTTON_A`：切换到上一步。
- `BUTTON_B`：切换到下一步。

第一步收到 `BUTTON_A` 时保持第一步并重新播报。最后一步收到 `BUTTON_B` 时结束当前服务并返回待机页。每次步骤变化都重新生成屏幕与播报指令，但地点 LED 在会话期间保持点亮。

### 6.7 浏览器 K10 模拟器

模拟器布局参考用户提供的效果图：左侧为六地点纸板地图示意，右侧为 K10 屏幕和操作区域。界面需要展示：

- 大字号作品名称和当前状态。
- 麦克风入口及文字测试框。
- 当前服务、步骤序号、步骤标题和说明。
- A 上一步、B 下一步两个大按钮。
- 扬声器正在播报或已完成的状态。
- 六个与地点对应的 LED，目标地点使用明显暖色点亮。

页面使用原生浏览器语音合成播报。用户关闭语音或浏览器不支持时，文字显示和按钮操作仍然完整可用。

## 7 接口设计

电脑端提供版本化 REST 接口：

- `GET /api/v1/health`：返回服务和当前模型提供者状态。
- `POST /api/v1/query`：提交查询并创建会话，返回完整设备状态。
- `GET /api/v1/sessions/{session_id}`：读取当前会话状态。
- `POST /api/v1/sessions/{session_id}/events`：提交 A/B 按钮事件，返回更新后的设备状态。
- `GET /api/v1/knowledge/services`：开发模式下查看演示知识记录。

浏览器第一阶段使用 REST 请求，不引入 WebSocket。查询期间显示进度状态；按钮事件完成后立即刷新状态。该交互量不需要长连接。

## 8 后续实体 K10 接口

未来串口适配器使用 UTF-8 JSON Lines，每行是一条消息。设备到电脑发送查询或按钮事件，电脑到设备发送完整设备状态或单项动作。消息保留 `version`、`type`、`request_id` 和 `payload` 字段，便于发现重复或过期消息。

首版只实现串口消息的数据模型、编码和解码测试，不打开真实串口，也不依赖具体 COM 端口。接入 Mind+ 时可以在不改动智能体核心的情况下实现串口读写循环。

## 9 完整交互流程

### 9.1 已知服务

1. 用户说“我想报名参加书法班”。
2. 感知模块得到查询文本。
3. 检索模块命中书法班服务记录。
4. 规划层根据记录生成不超过六步的计划。
5. 校验器核对时间、地点、材料和步骤来源。
6. 会话进入展示状态，活动室 LED 点亮。
7. 屏幕显示第一步并自动播报。
8. 用户通过 A/B 按钮浏览步骤。
9. 最后一步按 B 后返回待机页并熄灭 LED。

### 9.2 未知服务

1. 用户询问知识库中没有的服务。
2. 检索结果低于最低置信度。
3. 系统不调用模型补全事实。
4. 屏幕显示并播报“当前资料中没有这项信息，请向社区工作人员确认”。
5. 所有地点 LED 保持熄灭。

### 9.3 含糊问题

只有在两个高置信度候选无法区分时，系统才返回一个简短澄清问题。澄清问题不要求老人填写表单，不连续追问多个条件。澄清完成后重新进行检索和规划。

## 10 异常与安全处理

- 空问题：提示用户重新说出要办理的事情。
- 模型超时或接口失败：显示“智能服务暂时不可用，请稍后再试”，不输出猜测内容。
- 模型非法输出：重试一次，然后使用知识记录固定生成。
- 关键字段缺失：指出缺失的时间、地点或材料，并提示工作人员确认。
- 无效地点编号：禁止点亮 LED，记录程序错误并向用户显示安全提示。
- 会话不存在或已结束：返回待机状态，不让页面崩溃。
- 重复或快速按键：使用当前会话状态进行幂等边界处理，不越过第一步或最后一步。
- 超长文本与控制字符：在接口层限制长度并清理不可显示字符。
- 提示词注入：用户文本只作为查询内容，不能覆盖系统规则；知识记录以数据字段传入，模型输出仍经过白名单校验。
- 隐私：不存音频，不采集身份证、电话和精确健康信息；日志只记录匿名请求编号、命中服务和错误类型。

## 11 测试与验收标准

### 11.1 自动测试

- 十个已知服务查询命中正确服务、地点和知识来源。
- 同一意图的多种老人常用说法返回一致服务。
- 五个知识库外问题全部进入人工确认流程。
- 含糊查询最多生成一个澄清问题。
- 模型返回错误服务、地点、时间或非法 JSON 时不会直接展示。
- 模型超时、断网和空响应能够安全降级。
- A/B 按钮不会越界，最后一步按 B 返回待机。
- 无效会话和重复事件不会导致服务异常退出。
- 六个地点与六个 LED 编号一一对应。
- OpenAI 兼容、Ollama 和模拟提供者使用同一接口契约。
- 串口消息模型可以正确编码、解码并拒绝非法消息。

### 11.2 人工演示验收

- 页面能完整演示语音或文字查询、检索、规划、屏幕显示、播报和 LED 点亮。
- “书法班报名”场景能完整走完所有步骤。
- 知识库外问题能明确提示工作人员确认。
- 关闭云端模型后可切换模拟提供者继续演示。
- 大字屏内容在普通笔记本屏幕上清晰可读，单屏不出现长段文字。
- 学生能够指出感知、规划、行动模块，并解释为什么系统不会随意编造社区信息。

## 12 示例数据与展示边界

演示社区、地点、时间、电话、材料和活动安排均为虚构数据。界面和说明文档需要明确标注“演示数据”。未来替换为真实社区资料时，应由社区工作人员审核，并记录资料更新时间和负责人；本阶段不实现该审核后台。

## 13 后续迭代顺序

第一阶段完成并通过测试后，按以下顺序扩展：

1. 使用 Ollama 实测 Qwen3 0.6B 的结构化输出和响应时间。
2. 实现 Mind+ 侧串口读写与 K10 屏幕、按钮、扬声器联调。
3. 接入 DFR1231 扩展板和六个实体 LED。
4. 用经过社区审核的真实资料替换演示知识库。
5. 根据老人试用记录调整字体、播报速度、按钮说明和服务别名。

这些迭代不改变第一阶段的核心接口，只替换模型、数据和设备适配器。
